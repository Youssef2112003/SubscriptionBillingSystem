#  Subscription Billing System

**A real-world backend system for managing customer subscriptions, invoices, and billing cycles — built with .NET 9, Clean Architecture, DDD, and CQRS.**

## Project Overview

This is a backend API that handles the full lifecycle of a subscription:
- Create customers
- Create subscriptions with a billing plan (Monthly/Yearly)
- Automatically generate invoices when a subscription is activated
- Generate recurring invoices based on the billing cycle
- Mark invoices as paid (with double-payment prevention)
- Cancel subscriptions (stops future invoices while preserving history)

I built this project to deepen my practical knowledge of **Domain-Driven Design (DDD)**, **Clean Architecture**, and **Command Query Responsibility Segregation (CQRS)**. It also includes advanced patterns like the **Outbox Pattern** and **Idempotent Commands** to ensure reliability in production-like scenarios.

##  Architecture

The solution follows **Clean Architecture** with strict separation of concerns across 4 layers:

```
SPS.Domain        → Entities, Value Objects, Domain Events, Repository Interfaces
SPS.Application   → Commands, Queries, Handlers, DTOs, Abstractions
SPS.Infrastructure → EF Core (SQL Server / InMemory), Outbox, Background Jobs, Caching, Email, File Storage
SPS.API           → ASP.NET Core Web API (Controllers, Swagger, Auth)
```

Each layer only depends on the layer directly inside it — the domain has zero external dependencies.

##  Tech Stack & Patterns

- **.NET 9 / C# 13**
- **ASP.NET Core Web API**
- **Entity Framework Core** (SQL Server & InMemory for testing)
- **MediatR** (CQRS)
- **FluentValidation**
- **Serilog** (structured logging)
- **JWT Authentication** (optional, but ready)
- **Swagger/OpenAPI**
- **xUnit** (unit testing)
- **Outbox Pattern** → ensures domain events are reliably dispatched after DB commits
- **Background Service** → runs on a timer to generate invoices for active subscriptions
- **Idempotent Commands** → prevents processing the same command multiple times (bonus)

##  Features & Business Rules

-  Activating a subscription generates the first invoice automatically.
-  Each billing cycle (monthly/yearly) a new invoice is generated by a background job.
-  Paying an invoice marks it as `Paid` and records the payment date.
-  An invoice **cannot** be paid twice (domain invariant).
-  Canceling a subscription stops future invoices but keeps all history.
-  All aggregate changes raise **Domain Events** (`SubscriptionActivated`, `InvoiceGenerated`, `PaymentReceived`).
-  Outbox table stores events and a processor publishes them to MediatR handlers.

### Prerequisites
- [.NET 9 SDK](https://dotnet.microsoft.com/download)

### Clone the repository
```bash
git clone https://github.com/Youssef2112003/SubscriptionBillingSystem.git
cd SubscriptionBillingSystem
```

### Configuration
Update the connection string in `SPS.API/appsettings.json`:
```json
"ConnectionStrings": {
  "DefaultConnection": "Server=.;Database=SPSDb;Trusted_Connection=true;TrustServerCertificate=true"
}
```

> If you don't have SQL Server, change `UseSqlServer` to `UseInMemoryDatabase("SPSDb")` in `SPS.Infrastructure/DependencyInjection.cs`.

### Run the application
```bash
dotnet run --project SPS.API
```

Navigate to `https://localhost:7008/swagger` (or the URL shown in the console). You'll see the interactive Swagger UI.

### Run the tests
```bash
dotnet test SPS.Domain.Tests
```

##  Design Decisions (Why I Chose This)

### 1. Invoice belongs to the Subscription Aggregate
An invoice cannot exist without a subscription, and paying an invoice must be done through the subscription to enforce that an invoice is not paid twice. That’s why `Subscription` is the aggregate root and has a method `PayInvoice(invoiceId)`, not the other way around.

### 2. Outbox Pattern instead of direct MediatR publish
In a real production system, if I dispatched domain events inside the `DbContext.SaveChangesAsync` and the transaction failed, we could publish an event that never actually persisted. The Outbox pattern guarantees that events are stored atomically with the domain changes and published *after* the commit. This makes the system much more reliable.

### 3. Idempotent Commands (Bonus)
When external systems (like payment gateways) send commands, they might retry them. To avoid double-payment or duplicate subscriptions, I added an `IdempotentCommandBehavior` that caches the response based on a unique `IdempotencyKey`. If the same key comes again, the cached result is returned without re-executing the handler.

### 4. Background Billing Service as a `BackgroundService`
I chose a simple `BackgroundService` that runs in the same process for simplicity. In production, you could replace it with **Hangfire** or **Quartz.NET** for more robust scheduling and retries — just like I did in a previous project at Wavz (Accelerated Payment).

### 5. Soft Deletes & Auditing
The domain entities implement `ISoftDeletable` and `IAuditableEntity`, and an EF Core interceptor automatically sets audit fields — a technique I've used in government projects to track all data changes.
